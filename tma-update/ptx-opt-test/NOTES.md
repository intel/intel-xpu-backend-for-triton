# PTX A/B Test — Findings

Hand-built before/after PTX for the `paged_kv_load` microbench, to inspect the
descriptor-update optimization at the lowest IR level before building any
compiler machinery. See [../bench-plan.md](../bench-plan.md).

## Files

| File | What |
|---|---|
| `paged_kv_load_kernel.ptx` | **baseline** — `tensormap_create` (full build) per loop iteration. Generated offline on XE4 via `paged_kv_load.py compile_for_target(stop_after="ptx")`, `--arch sm100`. |
| `paged_kv_load_kernel.optimized.ptx` | invariant build hoisted; only `global_address` replace + republish + acquire in the loop. **Generated by `ptx_hoist.py`** (was originally hand-edited; the script reproduces it). |
| `ptx_hoist.py` | scripts the hoist transform so the optimized PTX is reproducible/reviewable. Run: `ptx_hoist.py baseline.ptx out.ptx [--reloc-offset N]`. |
| `baseline-vs-optimized.diff` | unified diff of the two. |
| `*.ttir`, `*.ttgir`, `*.llir`, `*.source` | upstream stages, for reference. |

## What the optimization does (verified by counting)

Inside the loop body `$L__BB0_1`:

| | baseline | optimized |
|---|---|---|
| `tensormap.replace.tile.*` | **13** | **1** (global_address) |
| zero-fill `st.shared` | 1 | 0 |
| `cp_fenceproxy` (republish) | 1 | 1 |
| `fence.proxy...acquire` | 1 | 1 |

(13, not 16: ptxas/LLVM already CSE'd a few identical-immediate replaces in the
baseline. The point stands — 13→1.)

The hoisted block (12 invariant replaces + zero-fill) now runs **once** before
`$L__BB0_1`. The per-iteration cost drops to: 1 global_address replace +
cp_fenceproxy + acquire — the irreducible floor.

## KEY FINDING: the descriptor SMEM buffer overlaps the data tile

This is the non-obvious correctness constraint that the abstract design missed,
and it only became visible by reading the real PTX.

In the **baseline**, the SMEM layout is:

```
global_smem + 0      : descriptor staging (128 B)   <-- built here every iter
global_smem + 0..4096: data tile (16x128 bf16 = 4096 B)  <-- TMA dest, offset 0 or 2048
global_smem + 4096   : mbarrier (8 B)
```

The descriptor staging at offset 0 **overlaps** the data-tile region [0, 4096).
Evidence in the baseline PTX:
- descriptor base: `mov.b32 %r18, global_smem` (line 70), `cvt.u64.u32 %rd25, %r18` (line 129) → offset 0.
- data tile dest: `add.s32 %r38, %r18, %r45` where `%r45 = (warp_parity & 1) << 11` → offset 0 or 2048 (lines 216-217).
- mbarrier: `add.s32 %r37, %r18, 4096` (line 200).

This overlap is **safe in the baseline** only because the descriptor is rebuilt
from scratch every iteration *after* the previous iteration's data-tile load
clobbered offset 0. A `bar.sync` (line 196) separates the cp_fenceproxy publish
from the tile load that reuses the bytes. Classic transient-SMEM reuse.

### Consequence for the optimization

A **naive hoist is INCORRECT**: if we build the descriptor once at offset 0 and
keep it there, the first iteration's data-tile TMA copy overwrites it, and every
subsequent `global_address` replace edits garbage.

The fix (in `optimized.ptx`): give the persistent descriptor its **own
non-overlapping SMEM home**. Here it's relocated to `global_smem + 4224` (past
the data tile and the mbarrier at +4096), via a new register `%r48`. This means
the kernel's shared-memory allocation must **grow by 128 bytes** (4352 vs 4224).

That 128 B is the concrete, measurable form of the
"persistent SMEM costs occupancy" tradeoff from the design docs — it is no
longer hypothetical. On a kernel that is SMEM-occupancy-bound, this extra 128 B
(×descriptors ×pipeline-stages in the real case) is exactly what could erode or
flip the win.

## Regenerating the optimized PTX

```bash
python ptx_hoist.py paged_kv_load_kernel.ptx paged_kv_load_kernel.optimized.ptx
# optional: --reloc-offset N  (persistent descriptor SMEM offset; default 4224)
#           --check-against <file>  (warn if loop replace count differs)
```

`ptx_hoist.py` is conservative: it asserts every structural assumption (finds the
loop label + back-edge, the descriptor-addr cvt, the zero-fill, exactly one
`global_address` replace) and bails with a clear error rather than emitting
wrong PTX. It is scoped to the **single-buffer** pattern; the pipelined
ring-slot case is out of scope.

## Status / caveats

- **NOT ptxas-validated** — no `ptxas` on the XE4 dev box. First assembly +
  correctness check happens on the GPU box via the override mechanism. This is
  true whether the optimized PTX is hand-written or `ptx_hoist.py`-generated.
- **Hand-edited, single-buffer microbench.** The real unified-attention kernel
  is pipelined (multi-buffered ring slots) — that hand-edit is materially harder
  and is phase 2.
- **ptxas may reschedule.** The hoist is expressed in PTX; ptxas could in
  principle re-sink it. Inspect SASS (`cuobjdump -sass`) on the GPU box to
  confirm the hoist survives.
- **Register/alloc bookkeeping** in the hand edit (`%r<49>`, `%r48`, the
  relocated `+4224`) is best-effort and must be sanity-checked by ptxas.
